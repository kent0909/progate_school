# 調査・分析・設計の質の決まり（QUALITY）

2026-10-22、オーナーの指摘で作った。Coffee Inc 2 の分析で「褒められている所」が浅く、設計（DESIGN-RAMEN）に楽な打ち手・抜本的な開発を避ける打ち手が混ざっていた。その傾向の原因と、再発させないための決まり。

## 1. 何が起きたか（原因）

| 傾向 | 起きたこと | 原因 |
|---|---|---|
| 調査が浅い | Coffee Inc 2 の資料が攻略ブログと少数の口コミに偏った。褒め言葉は6行の箇条書き | 依頼文（BRIEF）の問いが「簿記に使える所」「避けるべき不満」だけで、**「なぜ長く遊ばれるのか」という肯定側の問いがなかった**。資料の種類の偏りを測るものがなかった |
| 分析が浅い | 変数（豆・物件・農園・不動産・株…）を一つずつ説明しただけで、その多さ・深さ・絡みを面白さの源として分析しなかった。不動産は「崩れの原因」としてだけ扱った | 分析の型が「仕組み → 簿記の論点への対応表」だった。**検査（research-check）が測るのは「読んだか・写していないか」という手続きで、洞察の深さは誰も測っていなかった**（手続きの検査に通ることが目標になった） |
| 楽な道を選ぶ | 上場を「2級の範囲外」で外す、子会社・ライバルを「簡単なAI」、隣町より先は「一覧だけ」、上手な手を3つに固定 | CLAUDE.md の「時間・作業量を理由に棄却しない」は**明示的に時間を理由にした棄却しか止めない**。「範囲外」「簡単な」「一覧だけ」は理由の形を変えた同じ棄却だった。**簡略化を一覧にして理由を問う場所がなかった**。今のコードの延長で作れる形に寄せる力が働いた |
| 浅さを見逃した | 私（取りまとめ役）が、浅い報告をそのままオーナーに要約して渡した | 届いた報告を**書いた本人以外が読んで判定する工程がなかった**。私の要約がさらに解像度を落とした |

## 2. 決まり（再発防止）

### 2.1 依頼文（BRIEF）の型
調査を頼むときは `docs/BRIEF-TEMPLATE.md` の型で書く。必ず入れるもの：
- **肯定側の問い**：「なぜうまくいっているのか・なぜ長く遊ばれる／売れるのか」を、否定側の問い（不満・失敗）と同じ重さで
- **ゲームの目的に照らした問い**：「簿記に使えるか」だけでなく「面白さ・自由度・リアリティにどう効くか」
- **資料の種類の目標**（下の 2.2）
- **捨てるときの理由の制限**（下の 2.4）

### 2.2 調査の報告に必ずある章（tools/report-check.js が機械で確かめる）
報告の先頭に `<!-- quality:v2 -->` を置き、次の章を持つ：
1. `## 問いの設計`：何を問い、何を問わなかったか
2. `## 資料の内訳`：資料の種類ごとの本数（一次資料・統計／実務者・業界／研究／事例／利用者の声の集まり／作り手の話／反対意見）。1種類が全体の半分を超えたら理由を書く
3. `## うまくいく理由`：成功・好評の仕組みを因果の鎖（A→B→C）で。並べるだけでなく、何と何が絡むから効くのか
4. `## うまくいかない理由`：同じく因果で
5. `## 反証と限界`：自分の結論に反する資料、資料が取れなかった所
6. `## 捨てた案と理由`：表。理由の欄の制限は 2.4

### 2.3 書いた本人以外が判定する
大きな報告・設計は、書いた担当とは別の担当が `## 3. 判定の基準` で判定してから、オーナーに出す。判定は OK／要補強／アウト。アウトは調べ直し・書き直し。取りまとめ役（私）は判定の結果も一緒にオーナーへ出し、要約で解像度を落とさない（褒め所・面白さの源は要約でも具体の変数名で書く）。

### 2.4 楽な道の台帳（設計書）
設計書は `## 簡略化の台帳` を持つ。「簡単な」「一覧だけ」「範囲外」「固定」「後回し」「省く」にした所を全部並べ、各行に：
- 簡略化しない場合の形（フル版）
- 簡略化した理由。**認める理由は 学習効果・面白さ・正しさ（会計・法令）・規約 の4つだけ**。時間・作業量・実装の難しさ・今のコードとの相性は理由にならない
- 「範囲外（2級の範囲外など）」は理由にならない。範囲外でもゲームとして面白いなら入れる（簿記の論点にしない形で）。外すならオーナーの決定を書く

tools/report-check.js は台帳がない設計書と、本文に台帳に載っていない簡略化の言い回しがある所を警告する。

## 3. 判定の基準（別の担当が使う）

| 軸 | OK の目安 | アウトの目安 |
|---|---|---|
| 問いの設計 | 肯定側・否定側の両方。ゲームの目的（面白さ・学び）に照らしている | 片側だけ。簿記への対応表づくりが目的になっている |
| 資料の幅 | 種類が4つ以上。利用者の声は数十件規模で数えて分類 | 1種類（攻略ブログ等）が中心。声は数件 |
| 深さ | 因果の鎖、数字は幅で、成功と失敗の対比 | 項目を並べた説明。「〜がある」で止まる |
| 良い面の分析 | なぜ効くかを変数の絡みで説明 | 褒め言葉の引き写し |
| 写し方の大胆さ | 最小の写し方と大胆な写し方の両方を出す | 今の作りの延長で済む形だけ |
| 回避の痕跡 | 捨てた案に正当な理由（2.4） | 範囲外・簡単・手間で落としている |
| 反証 | 自分に不利な資料を挙げる | ない |

## 4. 性悪説での割り振り・管理・品質の確かめ（2026-10-22 オーナーの指示。すべての依頼に適用）

前提：任せた相手（下請けの担当・Fable・そして取りまとめ役の私自身）は、**すきあらば手を抜き、自分に都合のよいように依頼を解釈する**ものとして扱う。過去の実例：検査の依頼文に面白さの観点が抜けていた／Coffee Inc 2 の褒め所を6行で済ませた／「範囲外」「簡単なAI」で抜本的な作りを避けた／浅い報告を私がそのまま要約した。

### 4.1 割り振るとき（依頼文）
1. **依頼の原文を貼る**：オーナーの言葉を要約せずにそのまま入れる。私の言い換えだけを渡さない（言い換えで観点が落ちる）
2. **受け入れの基準を、確かめられる形で書く**：「十分に」「詳しく」ではなく、数・章・表・比べる相手で（例：口コミ50件以上を分類した表、変数の一覧に深さ・絡み・解放時期の3列）
3. **手抜きの予想を先に書いて塞ぐ**：この依頼で起こりそうな手抜き・都合のよい解釈を3つ以上挙げ、依頼文で先回りして禁じる（例：「件数を数えずに"多くの声"と書く」「実装しやすい形だけ出す」「難しい論点を範囲外にする」）
4. **やらなかったことを書かせる**：成果に「やっていないこと・浅いままの所・推測の所」の章を必須にする。その章が空、または「なし」なら疑う

### 4.2 管理するとき
5. **自己申告を信じない**：「全件読んだ」「エラー0」「網羅した」は、私が成果物とツールで直接確かめる（件数を数える・ファイルを開く・検査を自分で走らせる・無作為に数件を突き合わせる）
6. **依頼の対応表**：成果に「依頼の対応表」（依頼の原文の一文ごとに、どこでどう応えたか）を必須にする。私が原文と1行ずつ突き合わせ、抜けたら差し戻す
7. **途中で抜き取り検査**：長い仕事は途中の成果（章ごとのコミット）を開いて、方向がずれていないか見る

### 4.3 品質を確かめるとき
8. **書いた本人以外が判定する**（2.3）。判定役にも同じ性悪説を当てる：判定役が甘いことも疑い、判定の根拠（行番号・件数）がないものは判定として認めない
9. **私自身を疑う**：オーナーに出す前に、オーナーの依頼の原文と私の報告を突き合わせる（依頼の対応表を私の報告にも付ける）。要約で落ちた観点がないか、都合の悪い結果を小さく書いていないか、「確かめた」と書いたものを本当に確かめたか
10. **確かめていないことは、確かめていないと書く**

### 4.4 tools/report-check.js が確かめるもの（形の検査）
quality:v2 の報告と設計書は、章「依頼の対応表」と「やっていないこと」を持つ。「やっていないこと」の章が空か「なし」だけなら警告する。

### 4.5 判定・確かめは全数（2026-10-22 オーナーの指摘「イヤ全部見ろよ」）
- 判定役・確かめ役への依頼文に「必要なだけ」「主なものを」「代表的な」と書かない（手抜きの余地を依頼側が与えることになる。実際に「必要なだけ開いて」と書いた依頼で、判定役は27本中12本しか開かなかった）
- 判定は、報告が引く資料の**全部**について、読了ノートと原文（research/raw にあるもの）の両方を開いて主張を突き合わせる。判定書に「読んだ範囲」の表（資料ごとに：ノートを開いた／原文を開いた／突き合わせた主張の数／食い違い）を必須にする
- 原文が消えている等で開けないものは、開けなかったと表に書く（開いたことにしない）
