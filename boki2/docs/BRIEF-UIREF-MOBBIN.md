## 3. 視点（ここが今回の芯）
- **「本来あるべきデザイン」として評価する**。いまの画面・いまのコード・PR #7 の設計に合わせて縮めない。「いまの画面のここを少し直す」は書かなくてよい（書くなら別の欄）
- 各実例は「この型を、本来のゲームのどの体験の芯に置くか」を書く。例：「1か月＝1ステージ」「帳簿＝ダッシュボード」「仕訳＝振り分けの操作」
- 最後に、担当の範囲で **「本来あるべき画面の設計の素案」**（画面の一覧・各画面の主役・情報の階層・操作・動き・その根拠の実例の番号）を書く。絵は要らないが、言葉で再現できる具体さで

## 4. 受け入れの基準
1. 実例 **30件以上**（担当ごと）。各件に Mobbin の `mobbin_url` の引用、見た所（部品・位置・色・文字・数字を3点以上）、効く理由（因果の鎖 A→B→C）、本来のゲームでの置き場所、悪い面・合わない理由
2. **引いた画面は全部 research-fetch で取得**し、読了ノートを書く：`node boki2/tools/research-fetch.js --src mobbin-mcp --coll screens --doc <画面の id> --url <MCP が返した image_url>`。ノートは `boki2/research/notes/mobbin-mcp/screens/<id>.md`（形は既存の50本と同じ。image_seen に60字以上の具体）。既に取得済みの id は取り直さない（ノートがあればそれを使う）
3. **取得した画像は自分で開いて見る**。番号を付けた一覧の画像（10枚ずつなど）を作って Read で開いてよい。縮小のプレビューだけで書かない。image_seen は自分で見た原寸（か一覧）から書く
4. 担当の範囲の問い（9章）をすべて検索する。検索の記録（種類・問い・結果のアプリ）を成果の末尾に。**1つの問いで済ませず、言い換え・別のアプリの名指し・flows も使う**
5. 本来あるべき設計の素案（3章）
6. 「反対の事実・悪い面」：オーナーの好み（動き・ドラッグ・Coffee Inc 2）と同じ向きの結論ほど、反対の材料を書く。PEDAGOGY の禁止（連続記録・ハート・課金・時間の圧などの量への報酬、PEDAGOGY 1.8・BIZ-UIREF K10）に当たる型は、その旨と、写すならどの部分かを書く
7. 章：「要点」「実例の台帳」「本来あるべき設計の素案」「反対の事実と合わない型」「やっていないこと」（空にしない）「依頼の対応表」（原文の各文に）「検索の記録」。数（実例の数・取得の数・開いた画像の数）は道具で数える
8. `node boki2/tools/research-check.js` のエラー0（mobbin-mcp の行を返事に写す）

## 5. 手抜きの予想（先に禁じる）
1. **いまの画面への小直しに逃げる**：「帯の字を大きく」「ボタンに絵を」のような今の延長で書く（禁止。本来あるべき姿を書く。オーナーの原文がそれを求めている）
2. **Mobbin の検索結果の縮小だけ見て書く**（禁止。取得した画像を開く）
3. **有名どころ（Duolingo）ばかり**：同じアプリは最大で全体の3分の1まで。お金・会計・経営（Square・Shopify・Stripe・freee 的な業務）、家計（Copilot・Monarch・YNAB）、投資、ゲーム的な学び、健康・習慣の進み具合など、領域を広げる
4. **業務の画面をそのまま写して事務の画面にする**：各件に「ゲームとして合うか」を書く
5. **件数を頭で数える**（スクリプトで）
6. **第1回（uiref-mobbin.md）の焼き直し**：既に引いた画面は番号で参照するだけにし、新しい画面を探す
7. **外部への通信を MCP と research-fetch 以外でする**（禁止。WebFetch・curl は使わない。Mobbin の頁 mobbin.com/screens/… は取らない）
