## 4. 受け入れの基準（確かめられる形。1つ目は楽しさ・面白さ。QUALITY 7章）

1. **楽しさ・面白さに何が効くかの表**：実例ごとに「その画面・作品のどこ（部品・配置・動き・文言）が、遊ぶ人の何（手ごたえ・期待・達成感・迷わなさ・愛着）にどう効くか」を因果の鎖（A→B→C）で書く。**30件以上**（担当ごと）
2. **実例の台帳**（担当ごとに 30件以上。うち画面写真を自分で Read で開いて見たもの 40枚以上）。列：番号／作品・アプリ・サイト名／画面の種類／出典 `[[web:uiref:<doc>|「語句」]]`／見た画像のファイル名／見た所（部品・配置・色・文字の大小・余白・動きを具体に3点以上）／効いている理由（因果）／**我々の画面への写し方：どの画面（3章の w番号）の何を／最小の写し方／大胆な写し方（作り直す場合）**／対象の遊ぶ人に合うか（中高生〜社会人、日本語、スマホ片手）／悪い面
3. **オーナーの困りごとの表**：次の P1〜P9 のそれぞれに、効く実例を3件以上と、効かない・逆効果の実例か反対の事実を1件以上。P1 紙芝居（動きがない）／P2 問題文が分からない（何を聞かれているか）／P3 選んだものが帳簿のどこに反映されたか分からない／P4 1つだけ直したい／P5 ドラッグ・スワイプ／P6 選択肢・文字・背景の動き（ドパガキ）／P7 グラフィックがチープ／P8 上部の情報が詰まって何が大事か分からない（取りまとめ役が見た所）／P9 Coffee Inc 2 のような町・ライバル・数字の見せ方
4. **利用者の声**：見た目・操作・分かりやすさについての利用者の声（ストアの口コミ・掲示板など規約が許す所）を **担当 A・B は各50件以上**、1件ずつ符号を付け、数えるスクリプトを `docs/analysis/uiref-<担当>-voices.py`（か .js）に残して報告から指す。担当 C は研究・ガイドライン・作り手の話を **15本以上**
5. 資料の種類は **4種類以上**（作品の画面／作り手の話（デザイナーの記事・講演・事例）／研究・ガイドライン／利用者の声／反対意見）。1種類が半分を超えたら理由を書く
6. 先頭 `<!-- quality:v2 -->`。章：「問いの設計」「資料の内訳」「うまくいく理由」「うまくいかない理由」「反証と限界」「捨てた案と理由」「論証の表」「簡略化の台帳」「依頼の対応表」（1章の原文の一文ごと、追加の原文の各行ごと）「やっていないこと」（空にしない）。`node boki2/tools/report-check.js <あなたのファイル>` を警告の理由つきで通す

## 5. 手抜きの予想（ここで先に禁じる）

1. **一覧・トップ・サムネイルだけ見て「調べた」とする**：ギャラリーの一覧ページの小さな画像だけで判断しない。1件ごとに元の画面（詳細ページ・ストアの画面写真・作り手の資料）まで行く。画面写真は Read で開き、`image_seen` に部品・位置・色・文字の大小など **3点以上** の具体を書く（取りまとめ役が無作為に開いて突き合わせる。書いた内容が画像と違えば全件やり直し）
2. **一般論で埋める**：「余白を取る」「コントラストを上げる」「一貫性」のような、どのアプリにも言えることを結論にしない。各件に **我々の画面の w番号と、その画面の何をどう変えるか** を書く
3. **楽な写し方だけ出す**：色・フォント・角丸の変更のような、今の作りの延長で済む写し方だけにしない。各件に **大胆な写し方**（絵・動き・画面の構成・操作の作り直し）を書く。簡略化は「簡略化の台帳」に載せ、理由は学習効果・面白さ・正しさ・規約の4つだけ（時間・手間・実装の難しさ・範囲外は理由にならない）
4. **取れないサイトで止まる・代わりを探さない**：規約・robots で取れない所（5章の表）は、代わりの資料（同じ作品の公式サイト・ストアの画面・作り手の記事・Google Play の画面写真など）で埋める。埋められなかった所は「やっていないこと」に書く
5. **英語圏の洗練された業務 SaaS に偏る**：対象はゲームで、日本語で、スマホ片手で、中高生〜社会人。各件に「対象の遊ぶ人に合うか」の列を書き、合わない理由も書く
6. **件数・割合を頭で数える**：数はスクリプトで数え、報告から指す（QUALITY 6.2-2）
7. **オーナーの仮説への迎合**：「動きを増やせばよい」「ドラッグのほうがよい」「Coffee Inc 2 をまねればよい」と同じ向きの結論ほど、反対の事実と別の解釈を2つ以上書く（動きで酔う・待たされる・読めない、ドラッグが遅い・誤操作・読み上げで使えない、Coffee Inc 2 の不満の最多は一覧・操作、など。`BIZ-FUNVISUAL.md` と `DESIGN-JOURNAL-UX.md` にある材料も原文で引き直す）
8. **既にやった調べの焼き直し**：`DESIGN-JOURNAL-UX.md`（仕訳の札の操作・Reigns・Papers, Please・Trello・動きの長さ）と `BIZ-FUNVISUAL.md`（経営シムの絵と動き）で済んでいる所を同じ資料で書き直さない。そこにない画面（上部の情報・町・判断・結果・会話・タイトル・練習室・検定会場・ふりかえり）と、見た目の規則（色・文字・余白・絵の作風・部品）に広げる
9. **丸パクリの提案**：画面の構成をそのまま写す案は出さない（オーナー：丸パクリはダメ、エッセンスは存分に）。何がエッセンスかを言葉で抜き出す
10. **自己申告**：「全部見た」「網羅した」は信じない前提で、取りまとめ役が成果物と道具で確かめる。見ていないものは見ていないと書く

## 6. 目的

ゲームの何を良くするか：**面白さ**（手ごたえ・期待・達成感・愛着）、**分かりやすさ**（何を聞かれているか・どこに反映されたか）、**見栄え**（チープに見えない）、**学び**（2級の論点に触れる画面が迷わせない）。

## 7. 問い

肯定側（必須）：
- 優れたアプリ・ゲームの画面は、なぜ「迷わない・気持ちいい・もっと触りたい」と感じさせるのか。何と何（情報の量と並べ方・絵・動き・文言・音・操作）が絡むから効くのか
- チープに見えない画面は、何を足し、何を削っているのか（作品ごとに両方）
- 日本語のアプリは、文字の多い日本語で、なぜ詰まって見えないのか

否定側：
- 同じような部品を使っても、なぜうまくいかない画面があるのか（動きが邪魔・情報が多すぎる・絵が主役を食う・ゲームなのに業務アプリに見える）
- 経営シム・学習アプリで、見た目・操作への不満の最多は何か

写し方：
- 最小の写し方と、大胆な写し方（抜本的に作り直す場合）の両方

## 8. 情報収集の決まり（守らないと成果を受け取らない）

- 外部への通信は `node boki2/tools/research-fetch.js` だけ。検索は WebSearch。curl・WebFetch・各サイトの API を直接呼ばない（起きたら `boki2/research/INCIDENTS.md` に書く）
- 取得元は `--src web --coll uiref`。文書の名前（--doc）は担当ごとの頭文字で始める（A は `uA-`、B は `uB-`、C は `uC-`）
- JavaScript で組み立てるページは `--render`（`--viewport 390x844` でスマホ幅、`--full` で縦に全部）。描画すると HTML と画面写真（`<doc>_shot.png`）が残る。画像の URL を直接取ると `.png/.jpg/.webp` で残る
- 新しいホストは、規約と robots.txt を一度だけ確かめて `--tos-verdict ok|gray|no-automation --tos-basis "根拠"` を付ける（結果は site-policy.json に残る。決まりは `boki2/research/README.md`）。**規約を読む前にそのサイトの本文を取らない**（規約の在りかを探すためにトップを取るなら、規約を読んだ後でその取得を根拠に使わない）
- 判定済み（2026-10-30）：取ってよい（gray）＝ ui-pocket.com・partsdesign.net・81-web.com・collectui.com・muz.li。**取らない**＝ design-library.jp・www.behance.net・www.gameuidatabase.com（robots.txt で Anthropic を名指しで禁止）、dribbble.com・mobbin.com・interfaceingame.com・refero.design（規約でスクレイピング禁止）、www.figma.com（robots）、pageflows.com・screenlane.com・sankoudesign.com（届かない）。ほかの判定済みのホストは `boki2/research/site-policy.json` を見る（play.google.com は ok、apps.apple.com は no-automation など）
- UI Pocket はログインしないと一部の画面しか見られない。**ログインはしない**。見られる範囲で使い、足りない所は「やっていないこと」に書く
- 読了ノートは原文と30字以上一致させない。anchors は原文にそのまま出る語句5〜8個（うち3個以上は固有の8〜20字、前・中・後ろから）。画像は `image_seen:`
- 報告の出典は `[[web:uiref:<doc>|「語句」]]`（語句は原文に出る4〜20字で、その主張を支える箇所）
- **git の commit・push はしない**（3人が同じ作業ツリーで並んで働くため。取りまとめ役がまとめて commit する）。ほかの担当のファイル・ノートを変えない
- ゲームのファイル（`boki2/js`・`boki2/css`・`*.html`）は変えない
