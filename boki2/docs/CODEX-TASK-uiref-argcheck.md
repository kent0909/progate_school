## 検査のしかた（受け入れの基準）
1. **対象は結論の全部**：BIZ-UIREF.md の 0章（要点）の各行、1章の診断、2章の各 P の「一致／割れ」、3章の各画面の推し、4章の規則の推し、7章の因果の鎖、11章の論証の表の各結論。1結論1行の表にし、件数をスクリプトで数えて書く
2. 各結論に QUALITY 5.2 の7つの観点：**向き**（資料と逆でないか）／**範囲**（銀行アプリ・英語圏のアプリ・宣伝の画面写真・★5の口コミから、日本語の中高生〜社会人の簿記ゲームへ持ってきてよいか）／**選び方**（同じ資料の反対の記述を落としていないか）／**飛躍**（静止画から動きの良し悪しを、1作品から一般を、宣伝の画面から実際の遊びを言っていないか）／**逆の結論を組む**（同じ事実から逆をできるだけ強く）／**都合のよさ**／**数字**（数・割合を検算）。判定は 妥当／弱い／不当
3. **都合のよさは2つの向きで**：①作り手の手間が減る向き（「動きは控えめに」「規則を決めれば絵は要らない」「今の部品の延長で足りる」）②オーナーの仮説に迎合する向き（「動きを増やせ」「ドラッグがよい」「Coffee Inc 2 をまねる」「チープの原因は絵」）。どちらも QUALITY 5.4 のとおり厳しく見る
4. **割れたまま残した論点**（1章の上部の帯の原因、チープさの原因、6章 #8 数字の動きの長さ、#16 書類の画面で先に結果を出すか など）：割れの扱いが正しいか（本当は資料で決着がつくのに割れたことにしていないか、逆に割れているのに一致と書いていないか）
5. **面白さの観点**：その結論どおりに作ると、遊ぶ人に何が見え、どこが作業・罰・待ちに感じられるか（QUALITY 7.1）。悪い面が書かれていない推しを挙げる
6. **肯定側**：なぜその参考がうまくいっているのかの説明が、変数の絡み（何と何が絡むから効くか）になっているか。「〜がある」で止まっていないかも1段落で書く
7. 「逆の結論」「別の解釈」「直し方」の各行に【確かめた】（ノート・報告の文・数で確かめた）か【問い】を付ける（QUALITY 6.3）

## 手抜きの予想（先に禁じる）
- 結論の一部（0章だけ・11章の表だけ）を検査して全部とする → 1の件数をスクリプトで数えて全部を表にする
- 書き手の論証の表（11章）を言い換えて「妥当」とする → 自分で逆の結論を組む
- 数を検算せずに写す → 報告が指すスクリプト（`uiref-merge-count.py` など）を走らせる
- 書き手の文を直して検査した形にする → 指摘だけ
- オーナーの仮説と同じ向きの結論を甘く見る

## 報告（PR の本文と検査書）
- 依頼の対応表（上の原文と、1〜7の各行）
- 結論の件数と、妥当／弱い／不当の数（スクリプトの出力から写す）
- 不当の一覧（結論・理由・直し方。直し方は【確かめた】か【問い】つき）
- 採ってよいか：よい／条件つき／だめ、と条件（行単位）
- オーナーに確認すべき点（選択肢の形で、見せる数つき）
- やっていないこと（空にしない。原文を開けないことによる限界を必ず書く）
