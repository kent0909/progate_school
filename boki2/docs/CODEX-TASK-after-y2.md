## 仕事1：lexicon-check を「画面ごと」に数える

**決まり（PEDAGOGY 7 の本文。10/24 にオーナーが承認）**
- **1つの画面（書類・計算）で、新しい科目名は2つまで**（守る決まり）。3つ以上の画面があれば、検査は失敗にする
- 1か月に新しい科目名は2つまでを**目安**にする。3つ以上の月は注意として出すが、検査は止めない

**やること**
1. `boki2/tools/lexicon-check.js --ramen` に、画面ごとの数え方を足す。「新しい」とは、その画面より前に、教えた（teach）か画面に出た科目名ではないこと。いまの月ごとの数え方の何を残し、何を置き換えるかを、PR の本文に書く
2. いまの台本（1〜4年目6月の全部の画面）で、画面ごとと月ごとの数を表にする
   - 画面ごとに3つ以上のもの：画面の id・科目名・月
   - 月ごとに3つ以上の月：その月の画面ごとの内訳
3. 画面ごとに3つ以上の画面が見つかっても、**台本を自分で分けない**。一覧を PR に書いて聞く（場面の分け方は設計の判断）。その間、その画面は検査が失敗したままにする。例外の一覧に入れて通さない

**受け入れの基準**
- 面白さ・学び：画面ごとに3つ以上のものを0件にできたか。できない画面が残るなら、その一覧を出す（新しい言葉が重なって分からなくなる画面を、遊ぶ人が見ないことに効く）
- わざと3つの新しい科目名を1画面に入れた資料で失敗し、2つなら通る対照の検査がある
- 月ごとに3つ以上の月は注意として出るが、終了コードは0のまま
- `AGENTS.md` の6つの検査が全部通る。ただし、仕事1が見つけた画面のせいで lexicon-check が失敗している場合は、その画面の一覧を付けて報告する

**手抜きの予想（先に禁じる）**
- 今の台本が通るように、数え方（「新しい」の決め方・数える場所）を後から甘くする
- 書類だけ数えて、計算・作業台・決算の画面を数えない
- 失敗する画面を例外の一覧に入れて通す
- 月ごとの注意を、黙って失敗にする（または、出さない）

## 仕事3：店長を雇う仕組み（**設計の案だけ。実装はしない**）

オーナーの承認を受けてから実装する。この仕事では、案を PR に書いて止まる。

**案に入れるもの**
1. いつ店長が要るか：何店から、または何の条件（社長の時間・店の数・距離など）で、店長を雇えるか・雇う必要が出るか。いまの「社長の時間の予算」や複数店舗の仕組み（world.js の店ごとの計算）とどうつながるか
2. 遊びの選択：雇う／雇わない／いつ雇うか／だれを（経験・給料の違い）。どちらにも損と得があること（片方がいつも得になる案は不可）。迷う理由を具体的に書く
3. 帳簿と試験：どの仕訳・計算が出るか（給料・賞与・法定福利費・本支店会計・部門別の損益など）。日商簿記2級の論点とのつながり。PEDAGOGY 7（1画面に新しい科目名2つまで）を守れるか
4. 数の置き値：給料・効き目などの値に幅（lo/hi）を付ける。出どころがまだない値は「出どころ未確立・仮の値」と書く。外部への通信はしない（調べ物が要るなら「やっていないこと」に書く。取りまとめ役が research-fetch で調べる）
5. 最小の案と、大胆な案の両方。大胆な案の例：店長ごとの性格や育成、店長に任せた店の判断が社長と違う
6. 「なぜうまくいくか」（肯定側）：ほかの経営ゲーム・実際の飲食の多店舗化で、店長を置くことが面白さ・現実味に効く理由。「なぜうまくいかないか」（否定側）：作業が増えるだけ・いつも雇うのが正解になる、などのおそれ
7. 捨てた案とその理由。理由は学習効果・面白さ・正しさ・規約の4つだけ。「範囲外」「手間」は理由にしない

**受け入れの基準**
- 面白さ（1つ目）：雇うか雇わないかで迷う場面が、少なくとも2つの店の状況で具体的に書かれている（数字の例つき）
- 選択肢ごとの損得の表
- 出る仕訳の例と、つながる2級の論点の一覧
- 置き値の表（lo/hi・出どころ・仮かどうか）
- 実装の範囲の見積もり：触るファイルと、要る検査

**手抜きの予想（先に禁じる）**
- 「〇店を超えたら必ず雇う」だけで、選択も損得もない案
- 置き値を出どころのある値のように書く
- 実装まで始めてしまう（この仕事では実装しない）
- 肯定側の理由を書かず、仕組みの説明だけで終える
