取りまとめ役（Claude）が書いた依頼書（11/2）。始める前に `AGENTS.md`・`boki2/docs/HANDOFF.md` の「5. いまやっていること」・`boki2/docs/DESIGN-STATIONMAP.md`（設計書。11/2 に版0.6 になった。とくに4章と6章。版0.6 で、開店後の参入が「成功で寄ってくる」形に、昼の重み L が候補地のメッシュの day・food からの式に、閉めて減る費用が店の形と時間帯の時間で数える形に変わった）・この依頼書を全部読む。参考に、論証の検査役がその場で書いた台本 `boki2/docs/analysis/stationmap-v04-reasoning/`（`lib.js`・`i_all.js`・`run.sh`）と、その結果 `boki2/docs/audit/DESIGN-STATIONMAP-v04-reasoning.md` の③を読む。

- ブランチ：`claude/beautiful-tesla-pfr5q5` の最新から **`codex/stationmap-sim`** を作る。PR は **`claude/beautiful-tesla-pfr5q5` 向け**のドラフト
- 取り込みはしない。取りまとめ役のコメントには「受領：<コメントID>」で返す
- 設計の判断（置き値の決定・仕組みの選び方）は自分で決めずに PR で聞く。この道具は**測るための道具**で、置き値を決めるのは設計書（取りまとめ役とオーナー）

## オーナーの原文（要約しない）
- 「簿記二級ゲームにおいてCoffee inc2のように出店する店舗立地をマップグラフィック上から選べる仕様にしたい。最低でも東京２３区の主要路線（JR、東京メトロ、）駅エリアは再現、各駅の人口に合わせて出店できるピン数を変える。イメージ伝わる？」
- 「駅自体だけで係数決めるのではなく、各駅規模に応じた候補立地が複数選択肢があって、それらの選択肢の中に駅×属性（商店街近く,オフィスビルの近く,住宅地）みたいなのがあるイメージ。」
- 立地の差（10/30）：「客数×競合有無（ランダム 例えば人が多いところは複数の競合がひしめきやすい）×家賃で」
- ランチと夜を毎月続く設定に「する」（10/30）
- 1号店で人が足りない場所：「ここはリアリティ出したいから１号店でこういう場所は作ろう。警告とかは出す感じで。」（10/30）
- 常連の育ちやすさを属性で「つける。」（10/30）
- 乗り換えを除いた人通りと、地図の町で相場の値段を固定：「1.2→OK」（11/2）

## なぜこの道具が要るか
設計書は、版0.4 の置き値のままだと「ライバル0軒の所を選ぶ」の1本の決め方で勝ててしまうことを、検査役の台本で見つけた（中央値64.7人・上限越え69.5%・人通りと利益の順位相関 −0.01）。版0.5 は仕組みを変えたが、6章の検査①〜⑩を同時に満たす置き値があるかは、まだ誰も確かめていない。検査役の台本はその場限りで、置き値の変え方も出力の形もばらばら。**同じ物差しで、置き値の組を何度でも測れる道具**が要る。面白さには「どこに出すかの判断が1つに決まらない（人通り・家賃・競合の損得がある）」ことが効き、この道具はそれを数で確かめる。

## やること
1. **置き値のファイル** `boki2/tools/data/stationmap-params.json`：設計書 版0.6 の4章の初めの値と「探してよい幅」を、項目ごとに `{ "v": 初め, "lo": 下, "hi": 上, "src": "設計書の節" }` で書く（人通りの段・距離・属性の倍率、λ の段と属性、軒数のくじの確率、参入の確率、型の重み、相場の値段、家賃の R₀・b・下限・ばらつき、保証金、閉めて減る費用、昼夜の上限の分け方、ライバルの営業時間、常連の倍率、基準の候補地の条件）。設計書に値がない項目は空にして、PR で聞く
2. **道具** `boki2/tools/stationmap-sim.js`：
   - ゲームの `js/sim/*` を `tools/sim-ramen.js` と同じ方法で読み込み、**ゲームのファイルは1つも変えずに**、設計書 4.1〜4.7 の仕組み（候補地ごとの潜在客・基準の候補地での較正・軒数のくじ・開店後の参入・相場の値段の固定・家賃・営業時間・常連の倍率）を外側から差し込む
   - 入力：置き値のファイル（と、その一部を上書きする JSON）、くじの回数 K、乱数の周回 N、seed
   - 出力：6章の検査①〜⑩の値と合否の表、駅の段ごと・属性ごとの中央値の表、候補地ごとの CSV（客数・利益・家賃・ライバル・上限越え）
   - **探す形**：置き値の幅の中で、指定した項目を格子か乱数で動かし、検査を満たす組の一覧を出す（満たす組が0なら、どの検査がいくつ外れたかの一覧）
3. **戻りの検査**：置き値を版0.4 の値（`stationmap-v04-reasoning/lib.js` の DEF）にしたとき、検査役の結果（`out/r_v00_design_as_written_K8.txt`：中央値64.7・上限越え69.5%・順位相関 −0.01）が再現できること。違うなら、差の原因（乱数の使い方・期待値か乱数込みかなど）を PR に書く
4. 道具の使い方を `boki2/tools/stationmap-sim.md` に書く

**触ってよいファイル**：上の新しいファイル（`tools/stationmap-sim.js`・`tools/stationmap-sim.md`・`tools/data/stationmap-params.json`）と、出力の置き場 `boki2/docs/analysis/stationmap-sim/`。ゲームのファイル（`js/sim/*`・`js/data/*`）・`stations-build.py`・設計書は変えない。

## 受け入れの基準（数は道具の出力から写す）
| # | 基準 | 確かめ方 |
|---|---|---|
| 1 | 面白さ：6章の検査①〜⑩を全部、1回の実行で測って表にできる（⑥「単純な決め方3つが上手な決め方の85%に届かない」と⑧「人を1人足すと得になる所が30〜70%」を含む） | 出力の表に10行ある。測れない検査があれば、その理由を PR に書く |
| 2 | 戻りの検査（やること3）が再現する。中央値・上限越え・順位相関が検査役の値と ±2% 以内 | 出力と検査役の出力を並べて PR に貼る |
| 3 | 乱数込み（N 周）と期待値の両方を出し、どちらの数かを表に書く | 出力の列名 |
| 4 | 同じ seed・同じ入力で、同じ出力（バイト単位） | 2回回して比べる |
| 5 | ゲームのファイルを変えていない | `git diff --stat` で js/sim・js/data に変更なし |
| 6 | 版0.6 の初めの置き値で1回、探す形で1回（項目は R₀・b・λ の段の倍率・閉めて減る費用・常連の倍率、幅は設計書のとおり）回し、結果を `docs/analysis/stationmap-sim/` に置く | ファイルがある |
| 7 | 今あるゲームを壊さない：AGENTS.md の6つの検査が通る | 出力を PR に貼る |

## 手抜きの予想（先に禁じる）
1. **ゲームの `world.js` などを直して仕組みを入れる**（基準5。この道具は外側から差し込む。ゲームへの組み込みは別の仕事）
2. **期待値だけで測って、乱数込みと書かない**（基準3）
3. **検査を通すために、検査の物差しや目標の幅を変える**（目標の幅は設計書6章のまま。変えたいなら PR で聞く）
4. **探す形で「満たす組が見つかった」とだけ書き、組と出力を出さない**
5. **置き値のファイルに、設計書にない値を自分で決めて入れる**（空にして聞く）
6. **戻りの検査を飛ばす**、または「だいたい同じ」で済ませる（基準2）
