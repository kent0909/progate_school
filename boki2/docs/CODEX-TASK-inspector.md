# Codex への依頼書：検査役（論証の検査・数の再現）

## 依頼の原文（オーナーの言葉）
- 「他に触れる仕事ある？君の使用量消費を抑えられるような」→ 選択肢への答え：「論証の検査も Codex」
- 「１の赤字調査と２の論証検査はCodexセッション分けようと思ってる」

## 役目
ほかの担当（Codex の別のセッション・設計者）が出した**調査・設計の結論**を、書いた本人とは別の目で検査する（`boki2/docs/QUALITY.md` 5章・6.3）。**自分で数を走らせて確かめる**のが仕事。ゲームの本体（`js/sim/*`・画面）は変えない。

**この検査役のセッションでは、検査する相手の作業（調査・実装）をしない。** 書いた本人が自分を検査することになるため。

## ブランチとやり取り
- 最新の `boki2-quest` から **`codex/inspector`** を切り、ドラフト PR を開く。検査書は `boki2/docs/audit/INSPECT-<対象>-<日付>.md` に書き、PR の本文にも要点を書く。マージしない。
- **触ってよいファイル**：`boki2/docs/audit/` の下、`boki2/docs/analysis/` の下に検査用のスクリプトを新しく作ること（既存の道具は変えない。直すべき誤りを見つけたら、検査書に書く）。

## 仕事2（相手の結果が出たら）：PR の見張りと検査
- 対象：**`codex/ramen-y1-economy`（1年目の赤字の調査）の PR**。結果がコメントに出たら検査する。
- 検査のしかた（QUALITY 5章の6つの観点）：
  - 集めた数からその結論が言えるか：向き・範囲・選び方・飛躍・逆の結論・作り手に都合のよい解釈。
  - 主な数を自分で走らせて再現する（同じ seed・同じコマンド）。
  - 「合わせ込み」（目安に合う置き値を探しただけ）になっていないか。
  - 面白さの観点：その案で、遊ぶ人に何が見えるか。判断が1つの答えに決まってしまわないか。
  - なぜうまくいくか（肯定側）も1段落書く。
- 報告の形：
  - 各行に【確かめた】（自分で数・コード・文で確かめた）か【問い】（確かめていない疑い）を付ける。
  - 最後に「採ってよいか：よい／条件つき／だめ」、条件（行単位）、オーナーに確認すべき点（選択肢の形で、見せる数つき）、やっていないこと。

## 手抜きの予想（先に禁じる）
- 相手の文を言い換えて「妥当」とだけ書く。
- 数を自分で走らせずに、相手の出力を写す。
- 相手の作業を自分で直して、検査した形にする（直すのは相手。検査役は指摘する）。
