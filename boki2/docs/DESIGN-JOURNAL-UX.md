# 仕訳を書く画面の作り直し（設計）DESIGN-JOURNAL-UX

版 0.2（2026-10-25。版0.1 の論証の検査 `docs/audit/ARGCHECK-journal-ux-2026-10-25.md` の直す点11件に応えた。対応は「依頼の対応表」の末尾と「検査役の筋から採ったもの」）。依頼文は `docs/BRIEF-JOURNAL-UX.md`（追加の依頼「選択肢・文字・背景・ほうび・待たせない・強さ3段階・音」を含む）。決まりは QUALITY 4・5・7章。実装はしない（設計まで）。

オーナーの決定（覆さない）：**案B**（出来事を見出しにし、札には変わったものだけを書く）、ドラッグ（PC）・スワイプ（スマホ）＋押して選ぶ形も残す、意味のある動き、置いた札を1枚ずつ直す、問いに「何を手がかりに左右を決めるか」、最初の1枚はピヨの手本、同じ型の問い・「A：B」の札を全場面で洗い出す。

## 0. 要点（オーナー向け）

1. **いまの画面で何が起きているか**（1章）：プロローグの「ノートに書く」は、engine.js が台本の `title` と `label` を「親方に1万円借りた：小銭が増えた 10,000」の1文に組んでいる（`engine.js` 1206行）。台本の文そのものに「A：B」はなく、画面に出る8か所はすべて engine が組んだもの（2章、`docs/analysis/journal-ux-prompts.js` の出力）。動きは「左右が合わないときの横揺れ」1つだけで、札が棚や列に入る動き・数字が増える動きは0。
2. **問いの文と札の文の洗い出し**（2章）：ラーメン版の台本（`ramen.html` が読む `js/sim/*.js` 19本）から、問い173・札35・箱52・見出し3・engine が組む表示10の計273行を道具で拾った。仕訳・分類の問いと札の131行を表にし、36行を直す。道具の印は「A：B」10（全部 engine が組む表示）・手がかりなし14（語の一致。人が読むと直すのは8、残りは出来事の語に手がかりがある）・何の数か不明7。プロローグの note の画面は案Bで書き直した（3章）。
3. **操作**（4章）：札は「つかんで列に落とす（PC）／札の上で左右に払う（スマホ）／札を押してから列を押す（両方。同格）／Tab・矢印・Enter（キーボード）」の4つで同じことができる。置いた札は、列の中で押すと「左へ／右へ／棚へ戻す」が出て1枚ずつ直せる。しきい値（札の幅の 35%・速さ 0.3px/ms【推論・置き値。資料の数ではない】）未満は元へ戻る。WCAG 2.5.7（ドラッグの代替）と 2.5.1（経路ジェスチャーの代替）に合わせた。あてずっぽうで払う対策は、行がそろったあとの理由の1タップ（PEDAGOGY 1.3）・1回目に置いた列の記録・しきい値まで列を光らせない磁石（4.7）。
4. **動き**（5章）：1回の操作で動くものを「札→列→絵と数字」の3つに絞る。始まり（押して沈む）→途中（列が光る）→終わり（列に着地、小銭の絵と棚の帯と数字が変わる）。長さは種類で分け、手ごたえの動きは1つ 400ms 以下・1操作の時間の線で 700ms 以下（5.1 の線で足し算して示す）、教える動き（手本・せりふ）と背景は別枠で、押せば飛ばせる。数は全部【推論・置き値】で、資料の数ではない。紙芝居に見える場面12か所に動きを決めた。強さは「派手／ふつう／控えめ」の3段で、ふつうにはオーナーの承認した小さな画面の揺れと月替わりの暖簾を入れ、控えめは位置の変化を止め色と不透明度だけにする（WCAG 2.3.3 は止められることを求める。3段の設定で満たす）。音は押す・正解・お金の3つ、既定は WebAudio の自作、足りない分だけ効果音ラボの素材（規約で操作音への組み込みは再配布でない）。
5. **反映の見え方**（6章）：札が列に入った瞬間に、同じ画面の「棚」で、小銭の絵（屋台では小銭・寸胴の絵、店では口座の札）が動き、帯（資産／負債／純資産）が伸び、数字が増える。PC は3段の左の段、スマホは列の下の「棚の小さな絵」。変わった所だけ色を 1.2秒つける（NN/g の change blindness）。書類の画面では、置いた時点は「どの帯が動くか」だけ予告し（向きと額は出さない。Reigns の形）、「帳簿に書く」で本当に動く。
6. **学び**（7章）：橋渡しの言葉は、プロローグ（左右＝何があるか／どこから来たか。「へったら反対の列」は3行目の ask で遊ぶ人が見つける）→開店の前の最初の書類（列の見出しに「借方（左）＝何があるか」）→1年目9月（カード：権利も「もっているもの」）→決算①（マイナスの札は反対の列に書かない）の4段で言う。1画面180字・新しい科目名2つは守る（lexicon-check の数え方は変えない）。
7. **作る範囲**（9章）：作り直す順は ①note（プロローグ）→②docScreen（月の書類）→③sort/tap（プロローグ・発見）→④選択肢・文字・背景の動き（choice・card・理由・予想・名前の札・作戦の机・一杯・ふりかえりを含む全画面）→⑤月報・締め・開始記入。触るファイルは `engine.js`・`sim.css`・`ramen-y1.js`（note の台本）・`auto.js`（取っ手）・新しい `js/sim/journal-ui.js`。壊さない検査は AGENTS.md の6つ＋`ramen-y2-check`＋bot（取っ手は残す）。新しい検査は `tools/journal-check.js`（問いの手がかり・札の形・動きの長さの上限・取っ手の実在）。
8. **写し方**（10章）：最小（今の画面の作りのまま、札・動き・つかみ直しを足す）と大胆（帳簿を T字の盤にして、取引の札を直接そこへ入れる。月の書類も同じ盤で書く）の両方を書いた。**推しは「最小で作り、1年目の試遊で日常語の見出しの盤（いまの miniBS を広げた形）と列の形を比べ、段ごとに大胆へ寄せる」**：理由は正しさ・学び（T字に直接入れると「仕訳の行」を書く工程＝本試験の第1問の形の練習が消える。収益・費用の箱は4月末の d-sales まで出せない）と面白さ（札→列→棚の動きは最小でも全部入る）。版0.1 の理由「名前の前に T字は読めない」は外した（いまのゲームは名前の前から日常語の見出しで2列の棚を出している。`engine.js` の `miniBS`・`gw()`）。
9. **否定側（迎合の確かめ）**：オーナーの「ドラッグ・スワイプのほうが UX は良いのでは」と同じ向きの結論なので、反対の事実を先に書く。**この調査には、ドラッグ・スワイプが学びや評価を上げる証拠はない**（ドラッグ vs クリックの学習効果の一次研究は1本も読めず、プルダウン式のパブロフ簿記が高い評価）。スワイプはタップより遅く・誤りが多い（Yamanaka 2024、要旨）。払う操作は「考える前にできてしまう」ので、系統的な処理が要るもの（教育アプリのような）には最良の選択ではないと研究者が言う（Built In の Sundar の発言）。「1枚ごとに結果が返る・誤りは戻る」はこれを打ち消さない（外れたらもう片方へ払う試行錯誤を安くする向き）。だから本作の対策は、行がそろったあとの理由の1タップ（PEDAGOGY 1.3）・1回目に置いた列の記録・しきい値まで列を光らせない磁石・誤りのあとは文を閉じるまで同じ札を払えない、の4つで、効いたかは試遊で「1回目の正答率・反対へ払い直す率・払うまでの時間」を測って決める（4.7）。
10. **オーナーへの判断**：手本（A9。ピヨが最初の1枚を入れる）は「押せば一気に終わる」（待たせない）。メタ分析では系統がペースを決める動きのほうが効いた（Berney 2016）ので、1回目の手本だけは飛ばせない（1.5秒）にするか、飛ばせるままにするか。推しは「飛ばせるまま。飛ばした人には2枚目の前に 0.5秒の短い手本をもう一度」（待たせないを優先し、見なかった人にだけ補う）。

## 問いの設計

**何を問うたか**
- 肯定側：札を左右に払う・つかんで落とす操作は、なぜ気持ちよく、なぜ覚えやすいのか。うまくいっている例（Reigns・Tinder・Papers, Please・Trello）で、何と何が絡むから効いているのか。動きが学びに効く条件は何か
- 否定側：ドラッグ・スワイプが失敗する条件（誤操作・指で隠れる・スクロールとぶつかる・遅い・読み上げで使えない）。動きが邪魔になる条件（毎回待たされる・酔う・読めない・疲れる）。左右に払う操作が「あてずっぽうで払う」を招かないか
- 写し方：最小と大胆の両方。どちらを勧めるか
- 事実：いまの画面の問いと札の文を全部数える（道具で）。実際の画面を2つの幅で見る

**何を問わなかったか**
- 利用者の声の大規模な分類（口コミは42件。数十件規模だが、スワイプ操作の学習アプリの声は集めていない）
- ドラッグ操作の学習効果そのものの研究（取れたのは評価形式の比較の要旨と、動画 vs 静止画のメタ分析。ドラッグ vs クリックの学習効果の一次研究は robots.txt・Cloudflare で3本とも取れなかった。反証と限界）
- 音の効果の研究（音は規約と出どころだけ）
- 2年目以降の画面（t:'doc' は1〜4年目まで台本にあるので洗い出しには入れたが、画面の設計はプロローグと1年目の書類で書き、2年目以降は同じ部品で足りるかを「やっていないこと」に書いた）

**まずさの印の決め方**（道具の規則。道具が拾えない「分かりにくさ」は表の「何がまずいか」の欄に人が書いた）
- 「A：B」：文の中に全角コロンで2つの文をつないでいる（先頭8字以内の見出しの「摘要：」は除く）
- 手がかりなし：左右（列・棚）を選ばせる問いなのに、何を見て決めるか（何があるか／どこから来たか／増えた／へった／借方・貸方／返す約束／だれのもの／「手がかり：」の形）の語が文にない。置く先の名前（左の棚・右の棚・左の列・右の列）は手がかりに数えない（版0.1 は数えていて、「右の棚のどちら？」だけの問いを手がかりありにしていた。直した）。語の一致なので、出来事の語に手がかりがある問い（「借りた」「払う約束」）も印が付く。印の付いた14のうち、人が読んで直したのは8（prologue:3・4・5、d-capital、d-tax、d-allow、普通預金、docScreen は印なしだが直す）、残り6は「そのまま」と理由を表に書いた
- 何の数か不明：札に金額だけが付き、増えた／へった・何の額かが分からない
- 60字超：1文60字を超える（今回は0）

### 3.1 台本（`ramen-y1.js` の note の段）の書き直し

```
{ k: 'note',
  say: [['piyo', '忘れないように、ノートに書いておこう。1つの出来事を、左と右の2つの列に分けて書くピヨ。']],
  q: '出来事ごとに、変わったものを左と右に分けて書こう。左の列は、左の棚（何があるか）が増えたとき。右の列は、右の棚（どこから来たか）が増えたとき。',
  lines: [
    { title: '親方に1万円借りた',
      cards: [{ label: '小銭', delta: +10000, side: 'L', kind: 'up-L' },
              { label: '親方に返すお金', delta: +10000, side: 'R', kind: 'up-R' }] },
    { title: 'ラーメンが売れた',
      cards: [{ label: '小銭', delta: 'sale', side: 'L', kind: 'up-L' },
              { label: 'じぶんのお金（かせいだ）', delta: 'sale', side: 'R', kind: 'up-R' }] },
    { title: '材料を買って使った',
      cards: [{ label: '小銭', delta: '-cost', side: 'R', kind: 'down-L' },
              { label: 'じぶんのお金（つかった）', delta: '-cost', side: 'L', kind: 'down-R' }],
      ask: {（いまのまま：マイナスは書かない約束→反対の列）} },
  ],
  react: {（いまのまま：4つの返し）},
  demo: { line: 0, card: 0 },      // 最初の1枚はピヨが手本で入れる（3.3）
  after: [['piyo', 'ノートの左と右、どの行も同じ数。ノートを足し引きすると、棚の絵になるピヨ！']], showShelf: true }
```

変えるのは `label`（増えた／へったの語を消す）と `amt`→`delta`（符号つき）、`demo` の追加、`q`。`side`・`kind`・`ask`・`react` の文は変えないが、ask の働きは変わる：問いに「へったら反対の列」を書かないので、3行目の ask（「マイナスの数は書かない約束。小銭がへったことは、どう書けばいい？」）が遊ぶ人に見つけさせる発見のまま残る（版0.1 は問いが答えを先に言っていた。論証の検査 C14）。ask に正しく答えたあと、列の見出しの下に「へったときは反対の列」の1行を足して残す（7.2 #2）。文字数：ピヨのせりふ 45字＋問い 70字＝115字（180字以内）。1文の最長は問いの2文目 29字。

符号の扱い：手札では「小銭 −4千円」。右の列に着地した瞬間に「−」が 150ms で縮んで消え、「小銭 4千円」になる（列の見出し「右の列」が一瞬光る＝へったことを列が引き受ける）。ノートにマイナスの数は書かない約束（ask）と札の文が食い違わない。つかみ直して手札へ戻すと「−」が戻る。

```
│               │ │          [左の列] [右の列]   ← 押して選ぶ        │ │   1.2秒 光る │
│               │ │ ■ ラーメンが売れた（次）                   │ │             │
└───────────────┘ └──────────────────────────────────────────┘ └─────────────┘
```

### 3.3 最初の1枚はピヨが手本で入れる

- 段5の最初の札（「小銭 ＋1万円」）は、画面が出て 0.6秒後にピヨの手（小さな絵）が札をつかみ、左の列へ運んで置く（1.2秒）。置いた瞬間に左の棚の「小銭」の帯が伸びる。せりふ「小銭が増えた。左の棚のものが増えたから、左の列ピヨ」
- 手本の途中で画面を押すと手本は最後まで一気に進む（待たせない）。手本は1回目だけ。「もう一度見る」の小さなリンクを残す
- 手本の札は、遊ぶ人がつかみ直して直せる（手本は答えの見本で、動かせる）。2枚目から遊ぶ人が入れる
- 近道（3級既習、`lite`）でも手本は出す（段5は lite に入っていない）

### 3.4 間違えたときの返し

- 間違った列に落とすと、札は列の縁で止まり（吸い付かない）、0.25秒で手札の位置へ戻る。戻ったあとに、いまの `react[kind]` の文（「左の列は、左の棚（もっているもの）が「増えた」ときに書く場所」）をピヨのせりふとして出す。文は変えない（lexicon-check の対象）
- 戻ったあと、ピヨの文を閉じる（押す）までは同じ札を払えない（反対へ払い直すだけの試行錯誤を安くしないため。4.7）
- 2回目に同じ札で間違えたら、正しい列の見出し（「何があるか」）が1秒間だけ光る（答えは言わない。手がかりの場所を示す）
- 3つ目の行（材料）の `ask` は、札をつかんだ瞬間（手札の「小銭 −4千円」を引き始めたとき）に出す。いまは行に入る前に出るので、何を問われているか分かりにくい

## 4. 操作の設計（受け入れの基準3）

### 4.1 4つの入力で同じことができる

対象は「手札を列（左／右）に入れる」「入れた札をつかみ直す・戻す・入れ替える」の2つ。4つの入力はどれも同じ状態機械（4.3）の同じ遷移を起こす。

| 入力 | 入れる | つかみ直す・戻す・入れ替える | 根拠 |
|---|---|---|---|
| ドラッグ（PC、マウス・トラックパッド） | 手札を押したまま列へ運び、列の上で離す。約3ポイント（HIG の数。CSS px では約3px）動いたら「ドラッグ中の像」（半透明の複製）を出す。列の当たり判定は見た目より上下左右に 24px 広い【置き値】。札の中心が当たり判定に入ってから（しきい値を越えてから）列の縁が太くなる。それまでは光らせず、吸い寄せもしない（磁石を弱める。4.7）。離すと列の中心へ着地する | 列の中の札を押したまま反対の列へ運ぶ（入れ替え）、列の外（手札の場所）へ運ぶ（戻す） | HIG Drag and drop [[web:uiux:r11-ju-hig-dragdrop|「about three points」]] [[web:uiux:r11-ju-hig-dragdrop|「accept dragged content」]]、NN/g [[web:uiux:r11-ju-nng-dragdrop|「a magnetic effect」]] |
| スワイプ（スマホ、指） | 手札の上で左か右へ払う。札は指についてくる（軌道は問わない：指が上下にぶれても札はついてくる）。札の幅の 35% を越えて離す、または速さ 0.3px/ms 以上で離すと、その側の列へ飛ぶ。未満なら 0.25秒で手札の位置へ戻る。縦の動きが横の 1.5倍以上のときはページのスクロールに渡す（札は動かない） | 列の中の札を押すとメニュー（4.2）。列の中の札を反対の列へ払うと入れ替え、下（手札の方向）へ払うと戻す | WCAG 2.5.1 [[web:uiux:r11-ju-wcag-pointer-gestures|「along a specific path」]]（軌道を問わない作りにする）、Yamanaka 2024 [[web:learnsci:r11-ju-yamanaka2024-tap-swipe|「higher error rates」]]（しきい値と戻りが要る） |
| 押して選ぶ（両方。同格） | 手札を押すと札が「持ち上がる」（影・1.03倍）。次に列を押すと入る。または、手札の下の「左の列に入れる」「右の列に入れる」のボタンを押す（いまの `data-note` のボタンを残す。手札と同じ高さで、スマホでは手札のすぐ下に常に出す） | 列の中の札を押すとメニュー「左へ」「右へ」「棚へ戻す」 | WCAG 2.5.7 [[web:uiux:r11-ju-wcag-dragging|「without dragging」]] [[web:uiux:r11-ju-wcag-dragging|「A sortable list of」]]、HIG Gestures [[web:uiux:r11-ju-hig-gestures|「not replace them」]] |
| キーボード（Tab・矢印・Enter・Esc） | Tab で手札に焦点。Enter または Space で「持ち上げ」。←→ で列を選ぶ（選んだ列の縁が太くなる）。Enter で入れる。Esc で持ち上げをやめる | Tab で列の中の札に焦点。Enter でメニュー、←→ で左へ／右へ、Backspace で棚へ戻す | NN/g [[web:uiux:r11-ju-nng-dragdrop|「keyboard accessible」]]、既存のノート `uiux/r2-uiux-apg-keyboard`・`r2-uiux-wcag22-focus-visible` |

### 4.2 置いた札をつかみ直す・戻す・入れ替える

- 列の中の札は、すべて「置いただけ」で、確定していない。確定は「行の左右がそろって、ピヨが○を出す」とき（4.3 の `settled`）。確定前はどの札も直せる。確定後も直せる（列の札を押す→メニュー→直すと、その行は未確定に戻り、棚の帯も戻る）
- 直す操作は「1枚ずつ」：いまの「ひとつ取り消す」（最後の1手だけ）はやめ、札ごとのメニューにする。「もどる」（段を戻す）は残す
- 入れ替え：左の列の札を右へ運ぶと、右の列の同じ行に入る。右にすでに札があっても入れ替えではなく「追加」（1行に複数の札がある出来事があるため）。同じ札を同じ列に2回は入れられない（ボタンは出ない）
- 戻す：列から手札の場所へ。手札の並びは元の順に戻る（並びを覚えておく）
- 動き：つかみ直したとき、列の札は 1.03倍で浮き、残った札は 100ms でつめる。戻したときは手札の場所へ 200ms で飛ぶ。棚の帯は 400ms で縮む（入れたときの逆再生）

### 4.3 状態機械（1枚の札）

```
idle（手札） --press--> lifted（持ち上げ。影・1.03倍）
lifted --move>3px--> dragging（像が指／カーソルについてくる。列の上で列が光る）
lifted --列を押す／←→Enter--> placed
dragging --release on 列（当たり判定内）--> placed（列へ 200ms で着地）
dragging --release 外 or しきい値未満--> idle（0.25秒で戻る）
placed/settled --列の札を押す--> menu（左へ／右へ／棚へ戻す）
menu --左へ／右へ--> placed（反対の列へ 200ms）  menu --棚へ戻す--> idle

【プロローグの note・tap・sort・発見の boxes/sort】正誤は離した瞬間
placed --正しい列--> settled-pending（行の相手が入るまで）
placed --誤った列--> blocked（列の縁で止まり 0.25秒で戻る。react の文。文を閉じるまでこの札は払えない）--閉じる--> idle
settled-pending --行がそろう--> settled（行に薄い色。棚の絵と帯が動く）--理由を1タップ--> done

【書類の画面（docScreen）】離した瞬間には正誤を出さない
placed --（どの列でも）--> placed（列に残る。「→ どの帯が動くか」の予告だけ）
「帳簿に書く」--> 判定（いまの post／対比の返し。置き直した回数を docLog に残す）
```

プロローグの note では、誤った列に置いた札は `placed` に留まらず戻る（正誤の判定は離した瞬間）。いまの engine の note は誤りを数えていない（`engine.js` 1231〜1235行は `react` の文を出して描き直すだけ。版0.1 の「いまと同じく誤答は数える」は誤りだった）。新しい設計では、1回目に置いた列を `S.noteLog`（札ごと：1回目の列・正誤・払うまでの時間）に残し、成長の記録に「1回目で置けた札」として出す（罰ではない。4.7）。誤った札を列に残さないのは「誤りも一度は反映する」（PEDAGOGY 1.2 拍3）と逆に見えるが、note の反映は棚の絵と帯で、列に誤った札が残ると棚が間違った側に動いて「どこに反映されたか」が二重に見える。誤りの反映は書類の画面の「？の行」で行う。書類の画面では、置いた時点で正誤を出さない（1枚ずつ正誤が分かると「帳簿に書く」の前に答えが分かる。論証の検査 C12）。置いた札がそろって「帳簿に書く」を押したあとに対比を出す（いまの作り。4.5）。

### 4.4 誤操作の扱い

| 起きること | 扱い |
|---|---|
| 指がすべった（しきい値未満で離した） | 0.25秒で手札の位置へ戻る。音なし。何も数えない |
| 途中で離した（列の外） | 同上。像は「蒸発」ではなく元へ戻る（札はなくならない） |
| 縦にスクロールしたかった | 縦の動きが横の1.5倍以上なら最初の 60ms でスクロールに渡す。札は動かない。列の当たり判定に札の中心が入ってから縁が光る（吸い寄せはしない。4.7）。数（1.5倍・60ms）は【置き値】で、NN/g が言うのはタップ・スクロール・つかむを見分ける「数ミリ秒の遅延」だけ（数も目的も違うので NN/g の名は添えない） |
| 指が札と列を隠す | 列の当たり判定を見た目より広く（上下左右 24px）、列の「光る」は列の縁の全周で見せる（指の下だけで光らせない）。札の像は指の 12px 上に出す【置き値】 |
| 同じ札を2回入れようとした | 2回目は入らず、列の中の札が 1.03倍で一瞬浮いて「ここにある」を示す |
| 連打（押して選ぶで列を2回押した） | 1回目で入る。2回目は列の中の札のメニューが開く（別の意味になるのを避けるため、入った直後 300ms は列の押下を無視） |
| ドラッグ中にブラウザのスクロール（PC） | 列が画面の外なら、列の方向へ自動スクロール（HIG の [[web:uiux:r11-ju-hig-dragdrop|「Scroll the contents of a」]]）。ただし note の画面は列が手札の真上にあるので、390 でも列と手札が同じ画面に収まる配置にする（3.2） |
| 読み上げ（VoiceOver・TalkBack）で使う | スワイプは読み上げの操作なので使えない。押して選ぶ経路だけ。札は `button`（名前「小銭 ＋1万円、手札」）、列は `button`（名前「左の列、何があるか」）。入ると `role=status` で「小銭 ＋1万円 を 左の列 に入れた」。8章 |

### 4.5 書類の画面（docScreen）での同じ操作

- 手札＝その書類で使える札（いまの `opts`：教わった札だけ、5〜8枚）。列＝借方（左）・貸方（右）。金額は、いまのとおり書類の数字を押すか打つ（札を列に入れたあと、札の右に金額の欄が出て焦点が移る）
- 札が足りない（1行に2枚以上）ときは、同じ札を同じ列に2回は入れられないが、違う札は何枚でも入る（いまの「＋行をふやす」をやめ、入れた分だけ行が増える）
- 「帳簿に書く」は残す（置いた札と金額がそろったら押せる。Enter でも）。押したあとの返し（1回目「？の行」、2回目「箱の動き」、3回目「別の事例の手本」）はいまのまま。書き直すときは、列の札を1枚ずつ直せる（いまはプルダウンを選び直す）
- 置いた時点の予告は「→ もっているものの帯」のように**どの帯が動くか**だけ（向き・額は出さない。Reigns の予告が「どのゲージがどれだけ」で向きを出さないのと同じ形。向きまで出すと、貸方に置いた「普通預金」が「−」と出て書類と合わないことが押す前に分かり、1回目の正答（`mastered`）が甘くなる）。「帳簿に書く」の前に置き直した回数は `docLog` に `fixes` として残す。`mastered` の判定（別の月に2回、ヒントなしで1回目から正しい）は変えないが、予告が答えの手がかりになっていないかは試遊で「置き直し率」を見て決める（4.7）
- 慣れた種類（`mastered`）は止めずに進む（いまのまま）。ただし札が列に入る動きと棚の帯は出す（動きは短いので遅くならない）

### 4.7 あてずっぽうで払う、への対策（論証の検査 C7 を受けて組み直した）

版0.1 は「1枚ごとに結果が返る・誤りは戻る」を対策として書いたが、これは2択で外れたらもう片方へ払う試行錯誤を安くする向きで、対策ではない（Reigns も1枚ごとに結果が返り、その Reigns に「じゃんけん」の声がある）。対策は次の4つ。どれも「検査役の筋から採ったもの」に、自分で開いた原文と一緒に書いた。

| # | 対策 | どこで | 根拠 |
|---|---|---|---|
| a | 行がそろったあと、理由を1タップで選ぶ（2択。片方は典型の誤り）。例：1行目「小銭が左の列なのは？」→「小銭は、何があるか（左の棚）のものだから」／「親方が持ってきたお金だから」 | note（3行とも）、発見の boxes/sort（既存の reasons） | PEDAGOGY 1.3「操作は偶然でも正解できてしまうので、操作のあとに必ず理由を選ばせる」 |
| b | 1回目に置いた列を記録し（`S.noteLog`）、成長の記録に「1回目で置けた札」を出す。罰にはしない | note・書類（docLog の fixes） | PEDAGOGY 10.6「成長の記録（得意・苦手）」 |
| c | 誤りのあと、ピヨの文を閉じるまで同じ札を払えない | note・発見 | 連続で高速に払う試行錯誤を止める仕組み（版0.1 は「払わせない」と書いて仕組みがなかった） |
| d | 磁石を弱める：札の中心がしきい値を越えるまで列を光らせず、吸い寄せもしない。離すまで確定しない | 全画面 | NN/g のノートの自分の注意「吸い付きを強くしすぎると考えずに投げられる」 |

効いたかを測る数（試遊。`tools/playtest` の log と `S.noteLog`・`docLog` から）：
- 1回目の正答率（note の6枚・最初の書類）：目安 70%以上【置き値】。それ未満なら手がかりの文（R1）を見直す
- 反対へ払い直す率（誤りのあと、文を閉じて 2秒以内に同じ札を反対へ払った割合）：目安 30%以下【置き値】。超えたら c の待ちを長くするのではなく、理由（a）を誤りの直後にも出す
- 払うまでの時間（札を持ち上げてから離すまでの中央値）：目安 1.0秒以上【置き値】。0.5秒未満が続く人は「読まずに払っている」と見て、手本をもう一度出す
- 置き直し率（書類で「帳簿に書く」の前に列を変えた割合）：予告（4.5）が答えの手がかりになっていれば上がる。目安 20%以下【置き値】

PEDAGOGY 1.3 との関係：note は「操作のあとに理由を選ぶ」をいま持っていない（発見の画面は持っている）。a はそれを note にも入れるもので、1行ごと（3回）になる。問いの文が増えるので、理由の選択肢は各 20字以内、1画面180字の中に収める（ピヨのせりふ 45＋問い 70＋理由の問い 15＋選択肢 2×20＝170字）。

## 5. 動きの台本（受け入れの基準1＋追加の依頼）

### 5.1 決まり

- 1回の操作で動くものは3つまで：**札**（移動）・**列**（受け取り）・**数字／棚**（変化）。同時に全部を揺らさない。NN/g [[web:uiux:r11-ju-nng-animation-purpose|「is overwhelming」]]
- 長さの上限は動きの種類で分ける（数は全部【推論・置き値】。資料の数ではない。版0.1 は上限が1つで、台本の A7・A9・A11・A14・A15 が自分の上限を超えていた。論証の検査 C11）：
  - **手ごたえの動き**（A1〜A8・A10〜A13・A16。操作に対する返し）：1つ 400ms 以下。1回の操作（押してから、手ごたえの動きが全部終わるまで）の**時間の線で 700ms 以下**。重ねて走らせるので足し算ではなく、線の終点で測る
  - **教える動き**（A9 手本・A14 せりふの1文字ずつ）：別枠。押せば 0（5.4）。上限は手本 1.5s・せりふ 1.5s
  - **背景・儀式**（A15 湯気・客・昼夜・暖簾）：別枠。操作を待たせない（操作と並行して走り、押下を止めない）。暖簾は 600ms
  - **色の残り**（A6・A7 の 1.2s の色）：動きの長さに数えない（位置・大きさは変わらず、色だけ）。WCAG 2.3.3 の「動き」の定義（色・不透明度は動きに数えない）と同じ線引き
  - HIG [[web:uiux:r11-ju-hig-motion|「Aim for brevity」]]。Material 1 の「300ms・400ms を超えると遅く感じる」は gzip のまま保存され語句の照合ができないので出典にしない（zcat で解けば読める。反証と限界）
- 3つの操作の時間の線（手ごたえの動きだけ。ms）：
  - note の1枚（押して選ぶ）：0〜80 押す（A1）→ 80〜330 札が列へ飛ぶ（A3）→ 330〜480 着地の潰れ→ 250〜650 小銭の絵と帯と数字（A6。札が列に近づいた 250 から始める）＝ **650 ≤ 700**
  - 行がそろった：最後の札の着地 330 から → 330〜480 行の色（A5）→ 480〜680 ○が弾む → **680 ≤ 700**（理由の1タップは次の操作）
  - 書類の「帳簿に書く」：0〜80 押す → 80〜380 列の札が帳簿へ流れる（A11）→ 230〜630 小銭の絵と帯と数字（A6）→ 380〜530 帳簿の行が出る（A7）＝ **630 ≤ 700**（そのあと色が 1.2s 残るが、動きの長さに数えない）
- 飛ばす：動きの途中でも押せば次へ進む。動きは `requestAnimationFrame` の補間ではなく CSS transition / Web Animations API で作り、`finish()` で一瞬で終点へ。HIG [[web:uiux:r11-ju-hig-motion|「cancel motion」]]
- 緩急：出るときは `cubic-bezier(.2,.8,.2,1)`（速く出て、ゆっくり止まる。BIZ-FUNVISUAL 11章 21 と同じ）、消えるときは短く（出る 200ms に対して 150ms）
- 読ませる文・問いの文は動かし続けない（出るときの 1回だけ）。NN/g [[web:uiux:r11-ju-nng-animation-purpose|「detecting motion」]]（周辺視野が動きを拾い、読みを妨げる）
- 強さ3段（5.5）に従って、どの段で何を止めるかを表で決める

### 5.4 待たせない（追加の依頼）

- 押せる状態は動きの始まりから（動きの終わりを待たない）。例：札が列へ飛んでいる最中に次の札を押せる。飛んでいる札はその場で終点へ（`finish()`）
- 手本（A9）・せりふの1文字ずつ（A14）・暖簾（A15）は、押すと一気に終わる
- 同じ種類の書類が「慣れた」（mastered）あとは、A11 の帳簿へ流れる動きを 150ms に縮める（止めはしない：どこへ入ったかは見える）
- 1回の操作の時間の線が 700ms を超える設計は作らない（物差しは「1回の操作」の1つ。journal-check が動きの定義表から線を組んで検査する。9.4）

- 音のある場面は3段とも同じ（音は強さの設定の外。別の設定で消す）

## 7. 学び（受け入れの基準6）

### 7.1 守ること
- 1画面に新しい科目名2つまで、1画面180字：台本の文は3章のとおり 131字。手札の札の名前は教わった札だけ（いまの `opts` の決まりのまま）。lexicon-check の数え方（`--ramen`、1画面の本文の長さ・新しい科目・発見・原理）は変えない。問いに足した手がかりの語（何があるか・どこから来たか・増えた・へった・反対の列）はプロローグで教わる日常語で、lexicon の会計用語ではない（`lexicon.js` の `read` に追加はない。実装時に `lexicon-check --ramen` で確かめる）

### 7.3 動きが学びに効く条件（肯定側の問いへの答え）
- 動画 vs 静止画のメタ分析は、全体で小さな正の効果（[[web:learnsci:r11-ju-berney2016-anim-meta|「effect size of 0.226」]]）。効くのは「変化そのものを学ぶ」とき。本作の動き（札がどの列へ入り、何がどれだけ増減するか）は変化そのものなので、筋は合う。ただし効果は小さく、多くの個別研究で有意差がない（動きは学びの主役ではない）
- 原文の分類では、効いたのは realistic・photo-realistic・schematic な絵（iconic）で、効きにくいのは analytical pictures・formal notation・symbols・**charts・diagrams・graphs**・maps（abstract）（[[web:learnsci:r11-ju-berney2016-anim-meta|「iconic representation」]]）。棚の帯（棒の高さで額を見せる）も数字も abstract の側。版0.1 は帯を iconic と読み違えていた（論証の検査 C6）。だから反映の動きには、**小銭・寸胴なべ・屋台・口座の札の絵そのもの**が動くこと（A6 の小銭の絵、A16）を必ず入れ、帯と数字はその補助にする
- 同じメタ分析で、系統がペースを決める動きのほうが学習者が止められる動きより効いた（[[web:learnsci:r11-ju-berney2016-anim-meta|「were system-paced」]]）。本作で教える目的の動きの代表は手本（A9）で、押せば飛ばせる。これは「待たせない」（オーナーの承認）とぶつかるので、0章 #10 でオーナーへの判断として出した（推しは「飛ばせるまま。飛ばした人には2枚目の前に短い手本をもう一度」）
- 原因と結果がつながる：Reigns は、払う前に「どのゲージが動くか」の予告が札の傾きと連動し（[[web:simgames:r11-ju-reigns-gigazine|「増減量の多さを示して」]]）、払った瞬間に結果が動く。本作の「列の上で帯の名前と額を予告→着地で動く」はこの型

**推し：最小で作り、1年目の試遊で「日常語の見出しの盤」と列の形を比べ、段ごとに大胆へ寄せる。** 版0.1 の理由「T字の盤は名前の前に読めない（PEDAGOGY 0.2）」は外した：PEDAGOGY 0.2 が禁じるのは用語を先に出すことで盤の形ではなく、いまのゲームは名前の前から `miniBS`（`engine.js` 135行。左に資産、右に負債＋純資産の2列の絵）を `gw()`（51行。知らない語は「もっているもの／返すお金／返さないお金」に置き換える）の日常語で出している。PEDAGOGY 1.3 も P1・P2 の操作を「B/S パネルの箱を増やす・減らす・別の箱へ移す」と決めていて、盤を直接操る形はこの作品の土台にある。組み直した理由は4つのうち正しさ・学び・面白さ：
- 正しさ・学び：T字の盤に札を直接入れると「仕訳の行」（借方／貸方の1行）を書く工程が消え、本試験の第1問の形（PEDAGOGY 0.3「処理」の層：所定の形で書ける）を毎月の書類で練習する機会がなくなる。仕訳→転記（盤）の2段を1年目は分けて通す
- 正しさ：収益・費用の箱は d-sales（4月末）まで出せない（1画面の新しい科目名2つ・困りごとの前に用語を出さない）。盤を最初から出すなら、4月は資産・負債・純資産の3つの箱だけの盤になる（これは miniBS と同じで、できる）
- 面白さ：オーナーの指摘（紙芝居・反映が見えない・1枚ずつ直せない）は最小の形で全部に動きが入る（5.3 の12か所）。大胆の形の面白さ（常時盤面・盤が育つ。REVIEW-ROUND2 (f) の Mini Metro／Factorio の常時盤面）は、1年目から左の段の「棚」を日常語の盤として常に出し（6章）、列から盤へ札が飛ぶ動きで先取りする
- 時間・作業量は理由にしない（CLAUDE.md）。大胆の形を捨てるのではなく、順番を後にする（簡略化の台帳 #1）

大胆の形へ寄せる段（版0.1 より前倒し）：①**1年目の最初の月（4月）の試遊**で、日常語の見出しの盤（資産・負債・純資産の3箱。miniBS を広げた形）に札を直接入れる形と、列の形を、同じ書類で比べる（1回目の正答率・直す回数・所要時間・「どこに反映されたか」の問いの答え）→②1年目の決算①で「会社の棚」を T字の盤で見せる（読むだけ）→③2年目4月の開始記入を T字の盤に直接書く（opening は既存）→④2年目の月の書類で「盤の上に書類が浮かび、札を直接入れる」を選べる設定（既定は①の結果で決める）。会計の教材で T字に入れる操作の事例（依頼文の肯定側の例）は調べていない（やっていないこと）

## うまくいく理由（因果の鎖）

**鎖1 払う・落とす操作が気持ちいいのは、生得的な動作×現実の写し×次が来る小さな緊張、の3つが絡むから**
スワイプは赤ん坊もする生得的な動作で、雑誌をめくる・服の棚を流す動作の写し（[[web:simgames:r11-ju-tinder-builtin|「an innate gesture」]] [[web:simgames:r11-ju-tinder-builtin|「through a magazine」]]）。Tinder の起源も、トランプの山の一番上を横へ投げる衝動（[[web:simgames:r11-ju-tinder-builtin|「the top card to the side」]]）。Sundar らの研究は、制御感・楽しさ・関与が上がると報告（[[web:simgames:r11-ju-tinder-builtin|「The Power of the Swipe」]]）。→ 本作では、札を「投げる」動作に「どの列に入るか」の意味を乗せる（鎖3）。利用者の声でも「スパスパやれるくせにはまる」（[[web:simgames:r11-ju-applion-reigns-reviews|「スパスパやれるくせにはまる」]]）。

**鎖2 操作が先、題材が後。2方向の判断は払う操作と形が合う**
Reigns は美術担当の「Tinder を真面目な題材に」から始まり（[[web:simgames:r11-ju-reigns-gamingtrend|「an idea from Mieko」]]）、人物も調子も操作から派生した（[[web:simgames:r11-ju-reigns-gamingtrend|「that initial mechanic」]]）。Papers, Please も「書類を動かすこと自体が楽しかった」から全体を組んだ（[[web:simgames:r11-ju-papersplease-gameinformer|「papers around was fun」]]）。→ 仕訳は本質的に「左か右か」の2方向の判断で、払う操作と形が合う。操作が左右の意味を体で覚えさせる（これは【推論】。論証の表 #2）。

**鎖3 予告→操作→結果が1秒以内につながると、どこに反映されたかが分かる**
Reigns は払う前に、札の傾きと連動して上のゲージに「動く印」が出て（[[web:simgames:r11-ju-reigns-gigazine|「ゲージに大小の点が表示」]]）、払った瞬間にゲージが動く（[[web:simgames:r11-ju-reigns-gigazine|「ゲージが増減します」]]）。NN/g は、静的な変化は見落とされる（change blindness）ので短い動きで目を運ぶと言う（[[web:uiux:r11-ju-nng-animation-purpose|「users see the feedback」]]）。ドラッグの並べ替えでは離す前の約100msの予告が自然さを作る（[[web:uiux:r11-ju-nng-dragdrop|「(roughly 100 ms)」]]）。→ A2（列が光る・吸い付く）→A6（帯が伸びる・数字が増える）の台本。オーナーの「どこに反映されたか分からない」への直接の答え。

**鎖4 磁石・ゴースト・戻る動きが、ドラッグの誤りを減らし「紙芝居」を消す**
HIG は、約3ポイント動いたら像を出し（[[web:uiux:r11-ju-hig-dragdrop|「about three points」]]）、受け取れる先だけ強調し（[[web:uiux:r11-ju-hig-dragdrop|「accept dragged content」]]）、失敗は元へ戻るか蒸発する動きで伝えると言う（[[web:uiux:r11-ju-hig-dragdrop|「scale up and fade out」]]）。NN/g の磁石（[[web:uiux:r11-ju-nng-dragdrop|「a magnetic effect」]]）。ただし同じノートに自分で「吸い付きを強くしすぎると考えずに投げられる」と書いたとおり、磁石はしきい値を越えるまで働かせない（4.7 d）。→ 列の当たり判定を広く・縁の全周を光らせ・誤りは戻る（4.1・4.4・A4）。動きは「意味のある動き」（どこへ入るか・入らないか）だけで、飾りではない。

**鎖5 動きが学びに効くのは「変化そのもの」を見せるときで、写実・図式の絵の動きと対にすると効く**
メタ分析：全体で小さな正の効果（[[web:learnsci:r11-ju-berney2016-anim-meta|「effect size of 0.226」]]）、効くのは realistic・schematic な絵（iconic）で、charts・diagrams・graphs・symbols（abstract）は効きにくい（[[web:learnsci:r11-ju-berney2016-anim-meta|「iconic representation」]]）。→ 数字の増加と棚の帯はどちらも abstract なので、小銭・寸胴なべ・口座の札の絵が動くこと（A6 の小銭の絵）を必ず対にする。版0.1 の「帯＝図式」は読み違い（論証の検査 C6）。

**鎖6 手がかりのある問いは、解説の評価と同じ向き**
パブロフ簿記の口コミで評価されたのは「〇〇だからまず貸方に〇〇を書く、という手順が分かる」解説（[[web:uiux:r11-ju-applion-pavlov2-reviews|「手順がよく分かる」]]）。→ 問いに「何を見て左右を決めるか」を入れる（2章 R1）ことは、この声の向きと同じ。Reigns の否定の声「説明がないのでフィーリングで選ぶしかない」（[[web:simgames:r11-ju-gplay-reigns|「フィーリングで選択するしかなくて」]]）の逆。

## うまくいかない理由（因果の鎖）

**鎖A スワイプはタップより遅く・誤りが多く・触る位置がずれる**（[[web:learnsci:r11-ju-yamanaka2024-tap-swipe|「higher error rates」]]）→ スワイプだけにすると誤操作が増える → しきい値・戻り・大きい標的・押して選ぶ経路（4.1・4.4・8章）。

**鎖B 払う操作は「脳が処理できる以上の速さ」で動作を促し、内容を吸収しない**（[[web:simgames:r11-ju-tinder-builtin|「their brain can process」]]、同じ研究者が、系統的な処理が要るもの（教育アプリのような）には最良の選択ではないと言う [[web:simgames:r11-ju-tinder-builtin|「the best design choice」]]。研究の結果ではなく聞き取りの発言）→ あてずっぽうで払う → 「1枚ごとに結果が返る・誤りは戻る」はこれを打ち消さない（2択で外れたらもう片方へ払う試行錯誤を安くする向き。Reigns も1枚ごとに結果が返るのに「じゃんけん」の声がある）。本作の対策は、行がそろったあとの理由の1タップ・1回目に置いた列の記録・誤りのあとは文を閉じるまで払えない・磁石を弱める（4.7）で、効いたかは試遊の数で測る。Google Play の否定の声「じゃんけんと変わらない」（[[web:simgames:r11-ju-gplay-reigns|「じゃんけんで何連続勝てるか」]]）が、手がかりなしの払う操作の行き先。

**鎖C 動きは注意を奪うので、多いと読めない・疲れる・酔う**（[[web:uiux:r11-ju-nng-animation-purpose|「detecting motion」]]、前庭の障害 [[web:uiux:r11-ju-wcag-anim-interact|「distraction or nausea」]]、頻繁な操作に動きを足すと毎回待たされる [[web:uiux:r11-ju-hig-motion|「that occur frequently」]]）→ 1操作3つまで・700ms 以内・押せば飛ばせる・読ませる文は動かさない・3段の設定（5.1・5.5）。

**鎖D ドラッグは長い距離・小さい標的で非効率になり、モバイルではファイルを移すのにドラッグよりメニューのほうが誤りが少ない（NN/g の例は Gmail のドラッグで、スワイプの話ではない）**（[[web:uiux:r11-ju-nng-dragdrop|「over long distances」]] [[web:uiux:r11-ju-nng-dragdrop|「less error-prone」]]）→ 列と手札を同じ画面に近く置き（3.2・4.6）、押して選ぶを「補助」ではなく「同格」にする。

**鎖E 同じ操作の繰り返しは単調に見える**（Reigns の声 [[web:simgames:r11-ju-applion-reigns-reviews|「すぐ飽きました」]]）→ 本作は操作が同じでも書類と帳簿の変化が毎回違うが、慣れた種類は自動仕訳に回す（既存の仕組み）。それでも作業に感じるかは試遊で見る（体験の検討 #5）。

**鎖F 動きは系統がペースを決めるほうが効いた、という結果と「押せば飛ばせる」は逆向きに読める**（[[web:learnsci:r11-ju-berney2016-anim-meta|「were system-paced」]]）→ 本作の動きは 0.3秒程度で学習者が止める余地がなく、飛ばすのは「見た人が先へ進む」ためで、理解の途中で止める操作ではない。矛盾は小さいが【推論】（論証の表 #6）。

## 反証と限界

- **自分の結論に反する資料**：
  - Sundar「教育アプリにはスワイプは最良の選択ではない」（鎖B）。本作はスワイプを「唯一の道」にせず、1枚ごとに結果を返す形で使うが、それで「あてずっぽう」が消えるかは試遊で測るまで分からない
  - NN/g「モバイルではメニューのほうが誤りが少ない」（鎖D）。本作の押して選ぶ経路はこの指摘を取り込んだが、スワイプが「誤りの増加」に見合う楽しさを足すかは測っていない
  - パブロフ簿記2級 lite はプルダウン＋金額の形で 4.6（評価数は原文の表示のとおり）。操作の形を変えなくても支持される証拠。ドラッグが評価を上げる証拠はこの調査にはない
  - メタ分析の効果は小さく（g=0.226）、多くの個別研究で有意差なし（[[web:learnsci:r11-ju-berney2016-anim-meta|「no solid empirical」]]）。「動きで学べる」は言えない。本作の動きは学びの主役ではなく、反映の見え方と手ざわりのため
- **自分のノートにある否定で、版0.1 が落としていたもの**（論証の検査 4章 #6）：HIG Gestures は、スワイプの標準の意味を「操作を出す・閉じる・スクロール」（[[web:uiux:r11-ju-hig-gestures|「dismiss views; scroll.」]]）、ドラッグを「要素を動かす」（[[web:uiux:r11-ju-hig-gestures|「Move a UI element.」]]）とし、よく知られたジェスチャーをアプリ固有の意味に使わないよう言う。「札の上で左右に払って列を決める」は標準の意味からずれる。だから本筋はドラッグ（要素を動かす）で、スワイプは札の上だけ・しきい値つき・押して選ぶと同格、とした（4.1）。NN/g の磁石は、自分のノートで「強くしすぎると考えずに投げられる」と注意した点を 4.7 d で採った
- **道具の規則の限界**：「手がかりなし」は語の一致で、出来事の語（「借りた」「払う約束」）に手がかりがある問いにも印が付く（14のうち人が直すのは8）。「A：B」は全角コロンだけで、改行や「、」で組む形は拾わない。版0.1 の道具は8字の見出しを除外して2か所を数え落としていた（直して数え直した：A：B 10）
- **取れなかった資料**：Höffler & Leutner 2007 の PDF（0バイト）、Ponce-Arias 2021（springeropen の robots.txt が Disallow: /）、Noor 2016（eprints.gla.ac.uk が Disallow: /）、Open University のブログ・CORE（Cloudflare）、Boston College（404）、Material 3 の本文（JS の殻）、Material 1（gzip のまま保存され research-check が語句を照合できない。zcat で解けば本文は読める＝資料がないのではなく保存の形の問題。research-fetch が gzip を解かないので道具の直しが要る）、VentureBeat・Fast Company・AppUnwrapper（確認画面）。**ドラッグ vs クリックの学習効果の一次研究は1本も読めていない**。検索の要約（研究の向きは「正答率は変わらず、速さと関与で差」）は根拠に使っていない
- **利用者の声は42件**で、スワイプ操作の学習アプリの声はない。口コミの符号は語の一致で機械が付けた（`journal-ux-voices.js` の規則：OP＝操作・サクサク・スパスパ・フリック・スワイプ・指先・動き、GUESS＝適当に・運要素・フィーリング・じゃんけん・説明がない…）。符号の結果：42件のうち操作を肯定 8・あてずっぽう／運／説明不足 6・流れを止める 6・キャラ 6・解説 6・飽き 4・その他 17（重複あり）。人が読み直した分類ではない
- **Yamanaka 2024 は要旨だけ**。誤り率の差の大きさは読めていない
- **置き値（全部）**：資料から直接は出ない【推論】の置き値。根拠に近いものは NN/g の「約100ms」（並べ替えの予告）と HIG の「約3ポイント」「短く」、Material 1 の「300ms・400ms を超えると遅い・大きい画面ほど長く（タブレットで約30%）」（gzip のまま保存され語句の照合ができないので出典にしない。zcat で解けば読める）。実装のあと試遊で動かす。版0.1 の一覧は漏れが多かった（論証の検査 C11）ので全部挙げる：
  - 操作：しきい値 札の幅の 35%・速さ 0.3px/ms、当たり判定 上下左右 24px、ドラッグ開始 約3ポイント、縦1.5倍でスクロールへ・最初の 60ms、像は指の 12px 上、入った直後 300ms は列の押下を無視、誤りの戻り 250ms、払う札の高さ 56px、手札 44×44px
  - 動き：押す 80ms・浮く 120ms（1.03倍）・沈み 2px、札が飛ぶ 200〜250ms、着地の潰れ 0.96倍、列の縁 100ms・消え 150ms、誤りの縁の揺れ ±4px 160ms、行の色 150ms・○ 200ms、小銭の絵 300ms、帯 400ms、数字 400ms、帳簿の行 150ms、メニュー 120ms、数字の光 100ms・飛び 250ms、「？」の行 80ms ずつ、選択肢 浮く 2px・弾む 1.03倍・引っ込み 150ms 不透明度 0.6、せりふ 1文字 30ms・最大 1.5s・大事な語 1.1倍、手本 0.6s 待ち＋300ms＋600ms＝1.5s・短い手本 0.5s、暖簾 600ms、揺れ 2px 120ms（派手 4px）、色の残り 1.2s、出るとき 200ms・消えるとき 150ms、上限 1つ 400ms・線 700ms
  - 試遊の目安（4.7）：1回目の正答率 70%、反対へ払い直す率 30%、払うまで 1.0秒、置き直し率 20%
  - 1280 と 390 で同じ長さにしている。Material 1 は大きい画面ほど長く（タブレットで約30%）と言うので、試遊で 1280 の長さを 1.3倍にした版も比べる
- **実際の画面は2つの幅で見たが、タッチの実機では見ていない**（Playwright の `hasTouch` の模擬）。指で隠れる問題の確かめは人の試遊

| 案 | 捨てた／残した | 理由（学習効果・面白さ・正しさ・規約のどれか） |
|---|---|---|
| スワイプだけ（押して選ぶを消す） | 捨てた | 規約（WCAG 2.5.1・2.5.7）。読み上げで使えない。学習効果（鎖B：あてずっぽう） |

| 札を置いた瞬間に棚の帯を動かす（書類の画面） | 捨てた（予告の薄い表示に） | 正しさ（帳簿に書く前の仮置き） |
| 動きを「フェードイン」だけで済ませる | 捨てた | 面白さ（依頼文の手抜きの予想）。意味のある動き（どこへ入ったか）にならない |
| 画面の揺れを「ふつう」から外す（版0.1 の案） | 捨てた（ふつうに小さな揺れを戻した） | オーナーの承認「画面が少し揺れる」。WCAG 2.3.3 は止められることを求めるだけで、3段の設定で満たす（論証の検査 2章 #3） |
| 効果音をすべて素材サイトから | 捨てた（既定は自作） | 規約（再配布の定義が広い。自作なら制約がない）。足りない分だけ素材 |
| T字の盤（大胆の形）を最初から既定に | 捨てた（1年目4月の試遊で列の形と比べてから決める） | 正しさ・学び（仕訳の行を書く工程が消える）。面白さは最小の形で先に入る。「名前の前に読めない」は理由から外した（10章） |
| 「ひとつ取り消す」（最後の1手）を残して札ごとの直しを作らない | 捨てた | 面白さ（オーナーの決定：特定の札だけ直す）。「最後の1枚を戻す」は bot の取っ手として残す |
| 問いの文の言い回しだけ変えて手がかりを入れない | 捨てた | 学習効果（鎖6。手抜きの予想） |
| 手本を「読み上げ」や「控えめ」で省く | 捨てた（控えめは手を出さず札だけ動く。読み上げは文で手本を言う） | 学習効果（最初の1枚の手本はオーナーの決定） |

## 体験の検討（仕様の候補ごと。QUALITY 7.1）

| # | 放っておくと遊ぶ人は何をするか | 何が壊れるか | 直す仕様 | その仕様で遊ぶとどう感じるか：良い面 ／ 悪い面（和らげる手） | 現実の裏づけ |

| 1 | スワイプが気持ちいいので、考えずに左右へ払って当たるまで繰り返す | 左右の意味を考える判断が消える（P1 の学び） | 払う前に手がかりを問いに出す。行がそろったら理由を1タップ（PEDAGOGY 1.3）。1回目に置いた列を記録して成長の記録に出す。誤りのあとは文を閉じるまで同じ札を払えない。磁石を弱める（4.7）。「1枚ごとに結果が返る・誤りは戻る」は手ごたえであって対策ではない | 良い：払う手ざわりは残る。悪い：理由の1タップが3行分増えて手数が増える・戻されるたびに止まる・「怒られた」感（和らげる：理由は2択で20字以内、戻りは 0.25秒で音なし、文はピヨの口調、記録は罰にしない） | Sundar「系統的な処理が要るものには最良でない」、Google Play「じゃんけん」。Reigns の「適当に選ぶと長続きしない」は外れに重い損（王が死ぬ）があるから成り立つ話で、損を消した本作の裏づけにはならない（論証の検査 C7） |

## やっていないこと

- **ドラッグ vs クリックの学習効果の一次研究を1本も読めていない**（3本とも取得できず）。「操作が左右の意味を体で覚えさせる」は推論のまま
- **実装していない**（依頼のとおり）。置き値（しきい値・当たり判定・動きの長さ・合計の上限）は資料から出ず、試遊で決める
- **タッチの実機で見ていない**。Playwright のタッチの模擬だけ。指が札と列を隠す問題は人の試遊で確かめる
- **2年目以降の書類80種類の配置を1つずつ見ていない**。手札が8枚を超える種類の有無、1行に3枚以上の札がある書類（`ans` の行数）の数を数えていない（簡略化の台帳 #3）
- **利用者の声は42件・2サイト**で、スワイプで学ぶアプリ（例：Duolingo の並べ替え）の声は集めていない。符号は語の一致で機械が付け、人が読み直していない
- **音の効果の研究を読んでいない**。音は規約と出どころだけ
- **Material の動きの指針は出典に使えなかった**（M3 は JS の殻、M1 は gzip のまま）。HIG と NN/g と WCAG で代えた
- **journal-check の検査4（動きの長さ）の形式**（動きの定義表をどう持つか）は実装の設計に任せた
- **名前の札（namings 39件）の問いのうち直したのは3件**。残り36件は「選択肢が手がかりになっている」として「そのまま」にしたが、1件ずつ遊ぶ人の目で読み直してはいない
- **calc（計算の作業台、90件）の問いは表に入れていない**（左右を問わない）
- **会計の教材で T字に入れる操作の事例**（依頼文の肯定側の例）を調べていない。Trello も資料がない（NN/g の記事の中の例だけ）
- **Material 1 を出典に使えていない**（gzip のまま。zcat で解けば読める。取り直すには research-fetch が gzip を解く直しが要る）
- **あてずっぽうの4つの対策（4.7）が効くかは試遊で測るまで分からない**。目安の数は置き値
- **版0.1 の論証の検査**（`docs/audit/ARGCHECK-journal-ux-2026-10-25.md`）は「直してから出す」。この版0.2 で11件に応えたが、直したことで変わった結論（推しの理由・あてずっぽうの対策・時間の線・予告の形・ask の扱い）の再検査はまだ
